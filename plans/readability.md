## Design (2026-11-04, settled by the coordinator; author may revise)

1. **Source of truth**: `data/institutions/src/<id>.yaml`, one per entry, plus `data/institutions/src/properties.yaml`. Keys mirror the engine schema (`InstitutionJSON`, `Property`) one for one, so nothing is lost; each rule additionally carries `plain` (one English sentence, who may/must/must not do what, when, or else what) and optional `choices` (the reading chosen, alternatives rejected, why). `source` stays the existing field.
2. **Deltas, not copies**: an entry may say `extends: <id>` with `rules_drop: [ids]`, `rules_add: [...]`, and overrides for `name`, `notes`, `expected_properties`, `pair`, `source_text`, `isomorphic_to`, `not_isomorphic_to`, `minimal_pair_of`. The MWPA chain, the companion triple, the kibbutz and footbinding pairs are written as deltas. A minimal pair is then literally a one-line diff in the source.
3. **Build**: `data/institutions/build.py` (stdlib + PyYAML) resolves `extends`, strips `plain` and `choices` unless the engine schema accepts extra keys, and writes `institutions.json` and `properties.json` with the same serializer settings as today. Migration test: the first build from auto-converted YAML must reproduce the committed JSON byte for byte; the golden diff (`phil rules diff`) must read 0 changed. `_gen_institutions.py` and `_gen_properties.py` are deleted in the same commit, and the dataset README's "edit the script" rule becomes "edit the YAML".
4. **Migration**: a one-off script converts the committed JSON into the YAML files, detecting deltas (an entry whose rule set is a superset-minus-drops of another's becomes `extends`). `plain` lines are NOT invented by the migration; they are added by a separate builder, one per rule, from the rule text and its `source`, and checked by the card-only seat.
5. **Cards**: `docs/cards/<id>.md` generated by `build.py --cards`: roles, the rules table (id, who, deontic, what, when, or else, plain, source), expected properties with kind, pairs as one-line diffs against the base entry, and the ablation line per rule when an `ablate` summary is given (`--ablate PATH`).
6. **CI**: `build.py --check` regenerates JSON and cards into a temp dir and fails on any diff, on a rule lacking `plain` or `source`, or on an `extends` cycle. Added to `.github/workflows/ci.yml` before `check-all`.
7. **Council**: ADR 0014 amendment adds the card-only seat: reads `docs/cards/` and the sources only, never the YAML or code, judges faithfulness per entry, and may answer "cannot tell", which fails the entry on legibility.
8. **Not in scope now**: the marriage-bundle goods-by-step table (generated when that batch exists); plain-language result rendering (interpreting-results.md format) beyond the ablation line.

## Handoff text, verbatim

## Readability and reviewability (applies to all new work)
Goal: a person who doesn't read code can check whether an encoding is
faithful to the real institution, and contest it.

Encodings
- One readable source file per institution (e.g. YAML), not edits to
  the generator script or the big institutions.json. Generate the JSON
  from these files.
- Every rule carries three things side by side: the formal rule, a
  plain-English sentence ("the spouse may make medical decisions when
  the patient can't"), and its source with a short quote or pinpoint
  citation.
- Every encoding choice that could have gone another way gets a note:
  the reading chosen, the alternatives rejected, and why.

Human-facing views (auto-generated, checked into the repo)
- An institution card per entry: roles, a rules table (who must / may /
  must not do what, or else what), and sources.
- Minimal pairs shown as a one-line diff ("rule R4: status=married ->
  designated_by=patient") so the single change is obvious.
- For the marriage-bundle sequence: a table of goods by step, showing
  which are still gated on marital status.
- Results in plain language using the sayable / not-sayable format
  from docs/interpreting-results.md.

Code
- Names match docs/glossary.md; comments explain why, not what.
- Small functions; no logic hidden in the generator.

Checks
- CI fails if a rule lacks a plain-English line or a source, or if
  cards are out of date with the encodings.
- Council gets a "card-only" reviewer: reads the cards and sources, not
  the code, and judges whether each encoding is faithful. If that
  reviewer can't tell, the encoding isn't legible enough yet.
